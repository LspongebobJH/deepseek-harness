## Purpose and Scope

This page details how a running DeepSeek Harness (`dsh`) instance is assembled from ordered patch layers, profiles, bundles, `cordis.yml` manifests, and the configuration catalog. Rather than operating as a monolithic application, `dsh` initializes as a dynamic Cordis service tree driven by declarative composition layers (`packages/bundle/base/cordis.patch.yml:1-15]`, `packages/bundle/web-app/cordis.patch.yml:1-12]`).

---

## Composition Layers: Profiles & Bundles

An instance is booted by selecting a **Profile**, which specifies runtime entry points and environment routing, and loading **Bundles**, which group related plugins and supply base configurations via `cordis.patch.yml` files (`packages/boot/app-boot/tests/profile-resolution.spec.ts:150-165]`, `packages/boot/plugin-manager/README.md:10-15]`).

### 1. Profiles & Package Routing

Profiles dictate environmental initialization parameters and resolve package dependencies via `profile-resolution` (`packages/boot/app-boot/src/profile-resolution/resolver.ts:1-12]`). The profile resolution engine compiles generational maps (`CompiledGeneration`) for ESM and CommonJS loaders to intercept bare specifiers and route them to profile-local or shared installation directories (`packages/boot/app-boot/src/profile-resolution/resolver.ts:73-86]`).

### 2. Bundles

Bundles organize package families into operational tiers using patch overlays (`packages/bundle/base/cordis.patch.yml:1-15]`, `packages/bundle/web-app/cordis.patch.yml:1-13]`).

- **`@deepseek-ai/dsh-base`**: Minimal plugin set required for any harness instance, inserting core rows over an empty profile root (`packages/bundle/base/cordis.patch.yml:1-15]`, `packages/bundle/base/package.json:2-4]`).
- **`@deepseek-ai/dsh-web-app`**: Overrides base configurations (such as session-query SQLite and system prompts) and injects web-specific host rows, transport layers, and the browser module roster (`packages/bundle/web-app/cordis.patch.yml:16-162]`).

## Plugin Lifecycle, Toggles & Plugin Manager

Plugin lifecycle and toggles are managed programmatically or via configuration by `@deepseek-ai/dsh-plugin-manager` (`packages/boot/plugin-manager/README.md:10-15]`).

- **Plugin Enable/Disable**: Toggling a plugin updates the `disabled` field in the last matching override within the profile's `cordis.patch.yml` file, matching by entry ID and module name (`packages/boot/plugin-manager/README.md:36-40]`).
- **Bundle Selection**: Toggling a bundle modifies the ordered `dsh.profile.bundles` list in the profile's `package.json` (`packages/boot/plugin-manager/README.md:40]`).
- **Validation**: `scripts/verify-cordis-config.ts` validates Loader entry metadata, checks that browser packages correctly declare their `dsh.client` blocks, and verifies preset plane separation (`scripts/verify-cordis-config.ts:1-80]`).

Sources: `scripts/verify-cordis-config.ts:1-80]`, `packages/boot/plugin-manager/README.md:10-48]`, `packages/boot/plugin-manager/tests/manager.spec.ts:1-80]`

## Configuration Mechanism & The Config Catalog

Harness instances are configured via YAML files processed by `cordis-plugin-loader` (`scripts/verify-cordis-config.ts:1-19]`). Configuration values can utilize JavaScript expressions prefixed by `!!js` to evaluate runtime state against the Cordis context (`packages/bundle/web-app/cordis.patch.yml:38-38]`, `packages/bundle/base/cordis.patch.yml:22-23]`).

## Inspection, Debugging & Configuration Rules

To verify complex compositions, `dsh` provides validation scripts and configuration inspection utilities (`scripts/verify-cordis-config.ts:60-88]`).

- **Configuration Validation**: `verify-cordis-config.ts` parses all configuration files across bundles and profiles, ensuring structural integrity and correct package resolution (`scripts/verify-cordis-config.ts:60-88]`).
- **Preset Separation**: Assertions prevent plugins from being active simultaneously on both host and preset planes, avoiding double-registration collisions (`scripts/verify-cordis-config.ts:137-153]`).

This page provides the technical foundation for setting up and developing DeepSeek Harness (`dsh`) locally. It covers the monorepo environment, the build system's dual-aggregate architecture, the `dsh` CLI and profile booting, the distinctions between Host and Client TypeScript aggregates, and the quality gate infrastructure.

## 1. Environment Prerequisites

The repository requires specific engine versions and tools to ensure stability across the plugin-based architecture and pnpm workspaces layout [package.json11-18](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L11-L18).

- **Node.js**: Supports versions `^22.19.0` or `>=24.0.0` [package.json8-10](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L8-L10). The Continuous Integration (CI) system validates compatibility across Node versions 22.19, 24, and 26.
- **pnpm**: Version `11.7.0` is pinned via `package.json` [package.json7](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L7-L7). If `pnpm --version` does not resolve, enable Corepack using `corepack enable`.
- **Git**: Version 2.26 or newer is required to support worktree-specific configuration extensions.
- **API Key**: A `DEEPSEEK_API_KEY` stored in a root `.env` file is required for running live model integration tests, headless demos, and end-to-end scenarios.

## 3. The dsh CLI & Profile Booting

The primary entry point to DeepSeek Harness is the `dsh` CLI command provided by the `apps/cli` package [apps/cli/package.json2-16](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/apps/cli/package.json#L2-L16). It manages launching the agent harness with various configuration profiles assembled from ordered patch layers of plugins.

### Command Modes & Examples

| Command | Purpose |
| --- | --- |
| `pnpm dsh --profile web` | Starts the Web UI host serving the browser client [apps/cli/package.json2-4](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/apps/cli/package.json#L2-L4). |
| `pnpm dsh --profile headless "task"` | Runs a single task in headless mode and exits [apps/cli/package.json52](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/apps/cli/package.json#L52-L52). |
| `pnpm run demo:ptc -- "task"` | Runs a headless plaintext chat (PTC) demo mode [package.json52-58](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L52-L58). |

### Profile Composition and Booting

Profiles define how the harness assembles its plugin layers and configuration during boot. The profile booting mechanism is implemented in `apps/cli/src/profile-boot.ts`, which loads plugin patches, config sources, and dependency injections [apps/cli/src/profile-boot.ts1-20](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/apps/cli/src/profile-boot.ts#L1-L20).

This boot sequence executes under a Node.js process invoked via the `tsx` loader with ES module semantics, requiring all packages to maintain strict ESM compatibility [package.json6](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L6-L6), [package.json150-152](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L150-L152).

## 4. Dual-Aggregate Build System: Host vs Client

DeepSeek Harness uses two isolated TypeScript aggregates to prevent declaration-merge collisions of the Cordis Framework's `Context` interface when it merges different services under the same keys on Host and Client sides [tsconfig.host.json1-10](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/tsconfig.host.json#L1-L10), [tsconfig.base.json1-15](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/tsconfig.base.json#L1-L15).

### Why Two Aggregates?

Both Host (Node.js runtime) and Client (browser runtime) codebases merge into identical `Context` keys while offering entirely distinct underlying services. Compiling both in a single TypeScript project causes symbol pollution and type collisions. The repository solves this via:

- **Host aggregate**: Node.js process code, agent runtime logic, execution tools, and server-side RPC remotes governed by `tsconfig.host.json` [tsconfig.host.json10-116](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/tsconfig.host.json#L10-L116).
- **Client aggregate**: Browser-side UI components, web apps, and client-facing RPC contracts governed by `tsconfig.client.json`.

### Build Pipeline & Data Flow

The build pipeline enforces a strict sequencing to generate RPC type definitions and compiler boundaries:

1. **Host Build (`build:lib:host`)**:  
   Compiles Node-side sources via `tsconfig.host.json` and bundles via `tsdown --env.DSH_BUILD_FACE host`, producing Typert reflection artifacts and remote service declarations [package.json24](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L24-L24).
2. **Client Build (`build:lib:client`)**:  
   Compiles browser sources via `tsconfig.client.json` consuming the generated Host-for-Client remote type contracts, then runs `tsdown --env.DSH_BUILD_FACE client` [package.json25](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L25-L25).

## 5. Quality Gate System

The repository enforces stringent code quality, formatting, and correctness through an automated "Quality Gate" system orchestrated by `scripts/run-gates.ts` [scripts/run-gates.ts1-42](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/scripts/run-gates.ts#L1-L42).

### Gate Modes & Execution

The gate runner accepts aggregate mode selectors (e.g., `ci-primary`, `ci-static`, `ci-coverage`, `check-all`) defined in `Mode` [scripts/run-gates.ts24-42](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/scripts/run-gates.ts#L24-L42). Concurrency is dynamically bounded based on available system parallelism or overridden via `DSH_GATE_CONCURRENCY` [scripts/run-gates.ts106-111](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/scripts/run-gates.ts#L106-L111), [scripts/run-gates.ts168-187](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/scripts/run-gates.ts#L168-L187).

- **`ci-static`**: Runs static linters like `oxlint` and dependency structure validations.
- **`ci-coverage`**: Executes test suites under Vitest with coverage enforcement [package.json53](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L53-L53).
- **`ci-snapshot`**: Validates model/user message outputs against expected golden snapshots [package.json63-65](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L63-L65).

## 6. Windows CI & Failover Strategy

DeepSeek Harness implements a two-tier Windows testing approach:

1. **Wine Channel**: Executes core Windows-targeted checks inside a Wine layer on Linux CI runners for rapid initial verification [package.json87](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L87-L87).
2. **Native Windows Gates**: Full native verification gates (`ci-windows-blocking`, `ci-windows-complete`) executed on dedicated Windows runner instances [package.json88-90](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/package.json#L88-L90), [scripts/run-gates.ts34-36](https://github.com/deepseek-ai/deepseek-harness/blob/ddefc45f/scripts/run-gates.ts#L34-L36).
